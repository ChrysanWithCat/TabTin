# 多智能体协同技术分享：可能追问与回答

> 适用场景：部门技术分享后的 Q&A 备稿。  
> 基本策略：回答时先承认边界，再回到主线——**这次分享不是证明某个工具全能，而是讨论 AI 时代团队如何接住个人 AI 工作上下文。**

---

## 0. 答疑总原则

### 0.1 先把主线说清楚

可以反复用这句话收束：

> 我今天想讲的不是“再造一个更强的 Coding Agent”，而是：当每个人都用 AI 变快以后，团队如何保存和传递工作上下文，让下一个人接得住。

### 0.2 避免过度承诺

涉及 TabTin 当前能力时，建议用谨慎表述：

- “从项目设计/代码结构看，它在朝这个方向做。”
- “Public Preview 阶段我不会把它说成生产级成熟方案。”
- “这里更值得讨论的是协作抽象，而不是马上替代现有工具。”
- “这个点需要结合真实 Demo 或源码进一步验证。”

### 0.3 回答节奏

推荐三段式：

1. **先直接回答问题。**
2. **说明边界或风险。**
3. **拉回主线：团队上下文接续。**

示例：

> 是的，保存上下文会带来信息量和权限治理问题，所以不能简单理解成“把聊天记录全存下来”。关键是把任务目标、引用材料、关键决策、失败尝试、已测/未测和责任边界结构化，让接手人不用重新考古。

## 1. 通用高频追问

### Q1：这场分享到底是在讲多智能体，还是在讲 TabTin？

**建议回答：**

主线是“AI 时代的团队协作断点”。多智能体只是中间的一个参照物：它暴露了主体之间信息传递会被摘要压缩、会损耗的问题。TabTin 处理的是同一个问题在人和人、人和 Agent 之间的版本。

所以不是为了证明 TabTin 是多智能体平台，而是借多智能体这条线说明：

> 协作的核心不是主体数量，而是上下文能否被完整、可验证、可继续地传递。

---

### Q2：为什么叫“从一个人爽，到一群人接住”？

**建议回答：**

因为现在很多 AI 工具已经让个人任务体验很好：写代码、调研、生成文档都更快。但团队协作并不会自动变快。一个人用 AI 做完以后，判断依据、Prompt、资料来源、失败尝试、风险假设往往留在个人对话框里。下一个人接手时看到的只是结果和一个摘要。

所以“爽”指个人效率，“接住”指团队能否承接这个人的工作上下文。

---

### Q3：什么叫“接得住”？有没有定义？

**建议回答：**

我对“接得住”的定义是：

> 接手人在不翻原始聊天记录、不依赖原作者口头补充的情况下，能在可接受时间内理解目标、约束、关键决策、未决风险，并继续产出可评审结果。

可以用几个指标衡量：

- 接手人首次理解时间；
- 补问原作者的次数；
- 因上下文缺失导致的返工率；
- 关键决策能否追溯到依据；
- 已测/未测信息是否清楚；
- 接手后的 Review 一次通过率。

---

### Q4：这是不是只是“写好文档”的问题？

**建议回答：**

一部分是文档问题，但不只是文档问题。传统文档通常保存的是结果，而 AI 工作过程中真正有价值的内容还包括：

- Prompt 和任务分解；
- 引用过的材料；
- Agent 试过但失败的路径；
- 为什么选 A 不选 B；
- 哪些测试跑过，哪些没跑；
- 哪些内容是 AI 生成，哪些是人确认过；
- 后续接手人应该从哪里继续。

这些信息如果靠人事后补文档，很容易漏。TabTin 这类工具的价值在于：把工作现场本身变成可交接对象。

---

### Q5：为什么不是用飞书文档、Notion、Confluence、Jira 或 GitHub PR 就够了？

**建议回答：**

这些工具能解决一部分协作问题，但它们的主抽象不同：

| 工具类型 | 主要保存什么 | 常缺什么 |
|---|---|---|
| 文档/知识库 | 结果、说明、总结 | 过程、失败尝试、Agent 操作轨迹 |
| Jira/项目管理 | 任务状态、负责人、排期 | 判断依据、上下文细节 |
| GitHub PR | 代码 diff、Review 评论 | AI 生成过程、Prompt、资料来源、未验证假设 |
| 聊天记录 | 原始对话 | 结构化状态、可检索决策、可交接视图 |
| TabTin 这类方向 | 工作现场、上下文、协作轨迹 | 当前仍需验证成熟度和治理能力 |

所以重点不是说现有工具没用，而是说：**AI 工作上下文正在成为一种新的协作资产，需要更原生的保存和交接方式。**

---

### Q6：如果只是把聊天记录保存下来，不就解决了吗？

**建议回答：**

不够。聊天记录是线性的，而且噪音很大。接手人真正需要的不是“全部历史”，而是结构化后的工作状态：

- 任务目标；
- 当前进展；
- 输入资料；
- 关键决策；
- 被否决方案；
- 已知风险；
- 已测/未测；
- 下一步建议。

所以更准确地说，不是“保存聊天记录”，而是“把 AI 工作过程整理成可接手的上下文包”。

---

### Q7：多智能体不是会增加成本吗？为什么还要讲？

**建议回答：**

会增加成本，所以我在分享里专门泼了两盆冷水。多智能体不是免费午餐，也不是同一个模型开三个实例互相点头。

多 Agent 有价值的前提是：

- 角色真的异质，比如实现、安全、测试、架构；
- 信息源或工具权限不同；
- 有明确评价指标；
- 有成本预算；
- 有人类仲裁点。

我讲多智能体，是为了说明一个更一般的问题：**多个主体协作时，信息如何不在汇报和摘要中损耗。** 这和 TabTin 关注的人与人之间的交接问题是同构的。

---

### Q8：TabTin 是要替代 Codex / Claude Code / Cursor 吗？

**建议回答：**

不是。我的理解是，TabTin 更像是补团队协作层，而不是替代单人 Coding Agent。

可以这样区分：

- Codex / Claude Code / Cursor 更擅长让一个人把任务做快；
- TabTin 关注的是这个任务做完以后，过程、上下文、判断、材料、责任如何被团队接住。

所以它们更像互补关系：一个解决“个人如何更快完成”，一个解决“团队如何持续接续和复用”。

---

### Q9：TabTin 当前成熟吗？能不能生产使用？

**建议回答：**

我会谨慎看待。它目前还是 Public Preview，不应该被包装成已经完全成熟的生产级方案。

更合理的态度是：

- 可以用它观察 Human-Agent 协作平台的产品方向；
- 可以拿低风险、非强合规场景做试验；
- 不建议一上来承载强权限、强审计、强保密的核心生产流程；
- 真正落地前，需要验证权限、数据隔离、审计、回滚、成本和稳定性。

---

### Q10：这套思路明天不用 TabTin 能不能实践？

**建议回答：**

可以。这也是第 13 页行动建议的意义。

即使不用 TabTin，也可以先推一个“AI 工作交接最小包”：

- 任务目标；
- 输入资料；
- 关键判断；
- 被否决方案；
- 当前状态；
- 已测/未测；
- 已知风险；
- 下一步建议。

先把团队交接标准建立起来，后面再看工具如何自动化。

---

## 2. 产品视角追问及回答

### Q1：TabTin 的目标用户到底是谁？

**建议回答：**

从这次分享的角度，我会把它理解为：面向 AI 深度使用团队的 Human-Agent 协作工作台。第一批最适合的用户不是“完全不会用 AI 的人”，而是已经在大量使用 AI，但开始遇到协作断层的团队。

典型包括：

- 研发团队；
- 产品/技术联合调研团队；
- 前后端测试协作频繁的项目组；
- 需要复盘、审计、交接 AI 工作过程的团队。

---

### Q2：它解决的是高频痛点，还是高级痛点？

**建议回答：**

当前看更像“高级但会越来越高频”的痛点。

当团队只有少数人偶尔用 AI，交接损耗不明显；但当每个人都用 AI 加速，问题会放大：每个人都生成得很快，但上下文分散在个人聊天框、IDE、PR、文档和群消息里，团队开始难以复盘、复用和接手。

所以它不是今天所有团队的刚需，但很可能是 AI 使用成熟团队的下一阶段问题。

---

### Q3：有没有可量化收益？

**建议回答：**

这正是需要验证的地方。可以从这些指标看：

- 接手人理解任务所需时间；
- 接手后补问原作者的次数；
- 因误解上下文导致的返工次数；
- Review 评论中“为什么这样做”的比例；
- 测试遗漏或需求误解导致的缺陷；
- Prompt / Skill / 调研流程的复用次数。

我不会说现在一定有多少百分比提升，但它至少给了我们一组可以衡量“AI 团队协作效率”的指标。

---

### Q4：TabTin 的北极星指标应该是什么？

**建议回答：**

如果让我定义，我会选：

> AI 工作接续成功率。

它可以拆成：

- 接手人不用问原作者也能继续推进的比例；
- 上下文包被复用的次数；
- 交接后返工率下降；
- 关键决策可追溯率；
- 团队 AI 任务从开始到可交付的整体周期。

不要只看 Agent 生成了多少内容，而要看这些内容能否被团队继续使用。

---

### Q5：为什么不等大厂工具自己补这个能力？

**建议回答：**

大厂工具当然可能会补，但它们的出发点通常还是单人生产力工具、IDE、聊天工具或项目管理工具。TabTin 这类项目有意思的地方在于：它把“团队上下文接续”放在产品中心。

是否能成为独立机会，要看它能不能做出三个差异：

1. 上下文不是事后摘要，而是任务过程中的原生对象；
2. 人和 Agent 不在聊天框里交接，而是在同一份协作工件上工作；
3. 执行过程可追溯、可复盘、可复用。

---

### Q6：TabTin 是协作平台、Agent 平台，还是 IDE 外挂？

**建议回答：**

我更倾向于把它叫做：

> 面向团队的 Human-Agent 协作工作台，或者 AI 工作上下文平台。

它不是单纯 IDE，也不是单纯 Agent 编排器，也不是共享文档。它试图把任务、上下文、协作文档、Agent、执行环境、审计记录放到一个工作现场里。

---

### Q7：什么场景最适合作为第一个试点？

**建议回答：**

建议选中等复杂、跨角色、低风险的场景，比如：

- 技术调研交接；
- 需求变更影响分析；
- 前后端联调问题排查；
- 测试用例生成与评审；
- Bug 复现与修复记录；
- 小型重构任务的交接。

不建议一开始就用在强保密、强合规、强审计的核心生产链路。

---

### Q8：团队协作会不会牺牲个人效率？

**建议回答：**

如果要求人手动补所有材料，确实可能牺牲效率。所以关键不是“增加流程负担”，而是让工具在工作过程中自动捕获上下文，再让人只确认关键判断。

短期可以先用轻量 checklist，长期要靠工具降低记录成本。

原则是：

> 小任务轻交接，大任务重交接；低风险轻记录，高风险强追溯。

---

## 3. 前端/体验视角追问及回答

### Q1：人和 Agent 同编具体是什么交互？

**建议回答：**

理想状态不是 Agent 在聊天框里吐一大段内容，然后人复制到文档里，而是人和 Agent 面向同一个协作对象工作。

比如：

- Agent 在文档中生成草稿；
- 人在旁边修改、批注、确认；
- Agent 的修改有可见标识；
- 每次关键变更能回到任务上下文和操作记录。

具体产品形态可以像 Notion / Figma 的协作体验，但多了 Agent 的操作轨迹、权限和责任边界。

---

### Q2：Agent 改了什么，用户怎么知道？

**建议回答：**

这需要 UI 明确表达，而不能只在日志里。可能的设计包括：

- diff 视图；
- Agent 操作时间线；
- 批注或变更气泡；
- “AI 生成 / 人已确认”状态；
- 可回滚的检查点；
- 关键决策卡片。

否则人和 Agent 同编会变成黑箱，用户不知道该信什么。

---

### Q3：如果不是甩摘要，那接手人会不会被信息淹没？

**建议回答：**

会有这个风险。所以“不是甩摘要”不等于“把所有细节平铺出来”。更合理的是分层阅读：

1. 第一层：任务状态和关键结论；
2. 第二层：关键决策、风险、已测/未测；
3. 第三层：引用材料、完整对话、工具调用、文件 diff。

接手人先看结构化摘要，需要时再展开证据链。

---

### Q4：冻结上下文在界面上应该长什么样？

**建议回答：**

我理解它应该像一个 Context Package，而不是一段聊天记录。里面至少包括：

- 任务目标；
- 当前状态；
- 相关文件和链接；
- 关键判断；
- 被否决方案；
- Agent 操作记录；
- 人类确认点；
- 已知风险；
- 下一步建议。

UI 上最好支持搜索、折叠、过滤和按角色查看。

---

### Q5：CRDT 能解决什么，不能解决什么？

**建议回答：**

CRDT 主要解决多人实时编辑时的数据合并问题，比如文本或结构化块的并发修改。但它不能自动解决语义冲突。

比如两个人同时改同一段文字，CRDT 可以让数据不丢；但两个 Agent 给出相反结论，还是需要 UI 标出冲突，并由人类或规则仲裁。

所以协同编辑的关键不只是 CRDT，还包括冲突展示、归因、回滚和确认机制。

---

### Q6：PPT / 表格 / 文档这些复杂对象怎么做协作编辑？

**建议回答：**

这取决于 TabTin 的具体实现成熟度。原则上可以有两种方式：

1. 文件级版本管理：简单，但只能看到整体文件变化；
2. 结构化对象编辑：更复杂，但能看到段落、单元格、页面元素级别的变化。

如果是产品方向，我认为它应该尽量向结构化对象靠，因为团队交接需要知道“哪个结论、哪个表格、哪页 PPT 被谁基于什么理由改了”。

---

### Q7：责任追溯会不会让协作氛围变成“甩锅”？

**建议回答：**

有这个风险，所以设计上要把追溯定位成“复盘和恢复”，而不是“甩锅”。

好的追溯应该回答：

- 当时为什么这么判断；
- 依据是什么；
- 哪些地方没验证；
- 谁做了最终确认；
- 出错后怎么回滚和修复。

重点是让团队减少重复踩坑，而不是事后追责。

---

### Q8：Agent 角色 / Skill 应该怎么配置？

**建议回答：**

理想上要分层：

- 开发者可以用 Markdown / YAML / 代码配置复杂 Skill；
- 产品、测试可以通过 UI 配置角色目标、检查清单、输入输出模板；
- 团队层面需要版本、审批、灰度和回滚。

否则 Skill 会变成少数高级用户的 Prompt 仓库，难以团队化。

---

## 4. 后端/架构/安全视角追问及回答

### Q1：冻结上下文到底冻结什么？

**建议回答：**

这是必须讲清楚的关键问题。理想的冻结对象不应该只有最终摘要，而应该包括几类信息：

- 任务目标和状态；
- 对话 transcript；
- 工具调用记录；
- 引用的文件、链接和文档；
- 关键决策和否决原因；
- 文件快照或 diff；
- 测试命令和结果；
- 人类确认点；
- 权限和审计记录。

但具体 TabTin 当前实现到什么粒度，需要结合实际版本验证。答疑时不要把设计目标说成已经全部实现。

---

### Q2：交接时接收人没有原始文件权限怎么办？

**建议回答：**

合理的权限模型不应该因为“交接”就绕过原权限。一般有三种处理方式：

1. 不展示无权限内容，只显示占位和权限提示；
2. 展示脱敏后的摘要或元信息；
3. 由资源 owner 显式授权后再共享。

这也是为什么“交接不是共享目录”。交接应该是受权限约束的上下文转移，而不是把整个本地 Workspace 扔给别人。

---

### Q3：Agent 的权限继承谁？用户、Workspace，还是单独授权？

**建议回答：**

理想上应该是最小权限模型：

- Agent 不应天然拥有超过触发人的权限；
- Workspace 决定可见资源边界；
- 高风险工具调用需要单独审批；
- 跨 Workspace 或跨人交接需要显式授权；
- 所有关键操作需要审计。

如果当前实现还没完全做到，就应该明确这是生产落地前必须验证的点。

---

### Q4：TabTin 的沙箱是什么级别？

**建议回答：**

这要区分定位。Codex / Claude Code 这类工具在 coding 执行上会非常关注命令沙箱、文件系统隔离、网络控制。TabTin 如果更偏团队协作层，它的沙箱成熟度可能不是最大强项。

答疑时可以说：

> 我不会把 TabTin 描述成比 Codex / Claude Code 更强的执行沙箱。它的价值点更偏团队上下文和协作现场。真正生产使用时，沙箱、网络、secret、权限隔离都需要单独验证。

---

### Q5：Secret 怎么隔离？Agent 能不能读 `.env`、SSH key、cookie？

**建议回答：**

原则上 Agent 不应该默认读取这些敏感信息。需要做到：

- Workspace 级别的文件访问边界；
- secret 默认不可见；
- 高风险文件访问需要审批；
- 日志和上下文冻结时避免把 secret 持久化；
- 支持脱敏和审计。

这个问题非常关键，如果工具做不到，就不适合放到强敏感生产场景里。

---

### Q6：MCP / Skill 会不会带来供应链风险？

**建议回答：**

会。Skill 和 MCP 工具本质上扩大了 Agent 的能力边界，也扩大了风险面。

需要控制：

- 工具 allowlist；
- 版本锁定；
- 来源校验；
- 权限声明；
- 高风险操作审批；
- 工具调用审计；
- 团队级禁用和回滚。

所以“方法固化为 Skill”是价值点，但不是无风险能力。

---

### Q7：Prompt injection 怎么处理？

**建议回答：**

Prompt injection 是所有工具型 Agent 都要面对的问题。尤其当 Agent 读取网页、Issue、README、共享文档时，恶意指令可能混进上下文。

防护思路包括：

- 区分可信指令和不可信内容；
- 外部内容进入上下文时标记来源；
- 高风险工具调用需要审批；
- Agent 不应因为文档内容就自动扩大权限；
- 审计日志记录外部内容如何影响操作。

这里不能说完全解决，只能说需要作为威胁模型重点处理。

---

### Q8：Shadow Git 和用户 Git 是什么关系？

**建议回答：**

从分享口径看，Shadow Git 的目标是：在不污染用户原始 `.git` 的情况下，为 Agent 操作和工作检查点保存历史。

可以这样解释：

- 用户自己的 Git 仍然是正式工程历史；
- Shadow Git 保存 AI 工作过程中的检查点或变更轨迹；
- 它用于回滚、复盘、交接，不应替代正式 Git；
- 需要关注存储位置、加密、GC、大文件、LFS、子模块和权限问题。

如果被追问具体实现，可以说需要结合源码或 Demo 进一步确认。

---

### Q9：执行可追溯要追溯到什么粒度？

**建议回答：**

理想粒度至少包括：

- actor：谁触发，哪个 Agent 执行；
- time：什么时候；
- context：基于什么上下文；
- tool：调用了什么工具；
- permission：经过了什么审批；
- diff：改了什么；
- reason：为什么改；
- result：执行结果和测试结果；
- approval：谁确认进入下一步。

只有文件 diff 不够，只有聊天记录也不够，需要能串起任务链路。

---

### Q10：和 Codex / Claude Code 对比是否公平？

**建议回答：**

对比一定要讲口径。Codex、Claude Code 都在快速演进，不能简单说它们“没有协作能力”。更准确的表达是：

> 它们的核心优化对象仍然是单人任务执行闭环；团队接续、上下文可验证迁移、跨人责任追溯不是它们最核心的产品抽象。

TabTin 的补位点是协作层，而不是 coding 深度或底层沙箱能力。

---

### Q11：AGPL 对企业使用有什么影响？

**建议回答：**

AGPL 比普通 MIT/Apache 更需要注意。简单说，如果企业只是内部研究试用，风险相对可控；但如果二次开发后通过网络向用户提供服务，可能触发源代码开放义务。

答疑时不要给法律结论，可以说：

> AGPL 是企业落地前必须让法务确认的点。今天我只把它作为开源项目和协作方向来讨论，不建议绕过合规评估直接生产化。

---

### Q12：Public Preview 下哪些能力最需要验证？

**建议回答：**

我会优先验证：

- 权限边界；
- 上下文冻结粒度；
- 人和 Agent 同编的冲突处理；
- 审计日志是否完整；
- Shadow Git 回滚是否可靠；
- Secret 是否会进入上下文；
- 成本和性能；
- 与现有研发工具链的集成能力。

这些验证完之前，不建议把它当成熟生产平台使用。

## 5. 测试/质量视角追问及回答

### Q1：怎么证明 TabTin 真的让团队“接得住”？

**建议回答：**

可以设计一个很简单的对照实验：

- A 组：只给最终代码/文档 + 简短摘要；
- B 组：给上下文包，包括目标、资料、决策、否决方案、测试结果、风险和操作记录；
- 接手人：不参与原任务的人；
- 任务：复述需求、找风险、继续做一个小变更、补测试用例。

比较指标：

- 理解耗时；
- 补问次数；
- 变更正确率；
- 测试遗漏数；
- Review 评分；
- 返工次数。

如果 B 组明显更好，才说明“接得住”不是感觉，而是可验证收益。

---

### Q2：冻结错误上下文，会不会让错误更权威？

**建议回答：**

会有这个风险。所以冻结上下文不能等于“盖章正确”。它应该保存状态和依据，同时标注：

- 哪些是事实；
- 哪些是模型推断；
- 哪些经过人确认；
- 哪些尚未验证；
- 哪些存在风险或反例。

冻结的目的不是让错误变权威，而是让后续人知道这个结论是怎么来的，从而更容易检查和纠正。

---

### Q3：测试最关心的已测/未测信息如何保存？

**建议回答：**

这是 AI 交接里非常关键的一项。交接包里至少要包含：

- 跑过哪些测试；
- 测试命令是什么；
- 测试环境是什么；
- 哪些测试失败过；
- 哪些场景没测；
- 哪些风险只是推测；
- 是否有覆盖率或日志；
- 如何复现。

没有已测/未测，接手人很容易误以为“AI 说完成了”就等于质量达标。

---

### Q4：CRDT 能解决并发编辑冲突，那能解决语义冲突吗？

**建议回答：**

不能完全解决。CRDT 能解决数据结构层面的合并，比如不丢字符、不丢块。但语义冲突需要额外机制。

比如：

- 一个 Agent 说接口要保留兼容；
- 另一个 Agent 说可以破坏兼容；
- CRDT 只能保存两个修改，不能判断谁对。

这时需要冲突提示、Review、测试验证和人类仲裁。

---

### Q5：如何防止流程变重，抵消 AI 提效？

**建议回答：**

不能所有任务都用同一个重流程。建议按风险分级：

- 小任务：只记录目标、结果、风险；
- 中任务：增加关键判断、测试结果、下一步建议；
- 高风险任务：增加完整上下文、审批、审计、回滚点、验收记录。

原则是：

> 交接材料的重量，要和任务复杂度、风险、接手概率成正比。

---

### Q6：怎样定义 AI 辅助任务的完成标准？

**建议回答：**

可以加一个 AI 任务 DoD：

- 结果文件/代码/PR 已产出；
- 任务目标清楚；
- 输入资料可追溯；
- 关键决策有理由；
- 被否决方案有记录；
- 测试范围和结果明确；
- 未验证假设已标注；
- 已知风险已列出；
- 下一步建议明确；
- 哪些是 AI 产出、哪些是人确认过的，有边界。

一句话：

> 没有上下文的完成，只是个人完成，不是团队可接续的完成。

---

### Q7：如何长期追踪质量收益？

**建议回答：**

可以按团队和任务类型追踪：

- 交接后的补问次数；
- 上下文包打开率和复用率；
- 交接后返工率；
- Review 评论类型；
- 测试遗漏导致的缺陷；
- 缺陷复盘时能否追溯到原始判断；
- 任务周期变化。

长期看，不只看 Agent 生成速度，而要看团队返工和重复沟通有没有下降。

---

### Q8：TabTin 适合哪些任务，不适合哪些任务？

**建议回答：**

适合：

- 需要多人接续的任务；
- 有明显判断链的任务；
- 需要复盘和审计的任务；
- 跨产品、前端、后端、测试的协作任务；
- 中长期会复用方法的任务。

不适合：

- 一次性很小的个人任务；
- 极度敏感且权限模型未验证的任务；
- 强监管、强合规但工具审计未成熟的流程；
- 只需要快速草稿、不需要交接的临时任务。

## 6. 现场备用短答版

### 6.1 如果有人质疑“这不就是知识库吗？”

不是。知识库存结果，TabTin 这类方向想保存的是工作现场：谁基于什么上下文，让哪个 Agent 做了什么，为什么这么判断，哪些地方没验证，下个人如何继续。

### 6.2 如果有人质疑“多 Agent 不就是浪费 token 吗？”

很多情况下确实浪费。所以多 Agent 的价值不在数量，而在真实异质性：不同角色、不同工具、不同证据源和明确仲裁机制。否则只是同模型互相附和。

### 6.3 如果有人问“TabTin 比 Codex 强在哪里？”

我不会说它 coding 比 Codex 强。它强的方向是团队上下文接续：把 AI 工作过程变成可交接、可复盘、可复用的团队资产。

### 6.4 如果有人问“能不能马上上生产？”

不建议直接上强合规、强权限生产流程。Public Preview 更适合先拿低风险协作任务试用，重点验证上下文冻结、权限、追溯、回滚和团队接手效果。

### 6.5 如果有人问“明天不用工具能做什么？”

推一个 AI 工作交接最小包：目标、输入、关键判断、否决方案、测试结果、未验证风险、下一步建议。先把交接标准建立起来。

### 6.6 如果有人问“为什么 AI 个人提效没有变成团队提效？”

因为个人速度只是局部效率。团队效率还依赖上下文传递、流程衔接、判断复用、质量验证和责任追溯。AI 加速了个人产出，也放大了交接损耗。

### 6.7 如果有人问“保存这么多上下文会不会信息过载？”

会，所以不能平铺全部历史。要分层：先给任务状态和关键判断，再展开资料、对话、工具调用和 diff。接手人要的是可接续视图，不是聊天记录考古。

### 6.8 如果有人问“AI 出错了，追溯有什么用？”

追溯不能保证 AI 不出错，但能帮助团队知道错误是怎么产生的、基于什么假设、谁确认过、怎么回滚、下次如何避免。它是质量复盘的基础。

## 7. 可直接放到第 13 页的 AI 工作交接 Checklist

**AI 工作交接最小包：**

- [ ] 任务目标：要解决什么，不解决什么；
- [ ] 输入材料：需求、设计稿、接口、代码、文档链接；
- [ ] 关键判断：为什么选这个方案；
- [ ] 被否决方案：试过什么，为什么放弃；
- [ ] 当前状态：完成了什么，没完成什么；
- [ ] 变更范围：涉及哪些文件、模块、数据；
- [ ] 测试结果：跑了哪些测试，哪些没跑；
- [ ] 已知风险：哪些假设尚未验证；
- [ ] 接手建议：下一个人从哪里继续；
- [ ] 责任边界：哪些是 Agent 产出，哪些是人确认过的。

推荐收尾句：

> 没有这些内容，不叫 AI 交付完成，只叫个人完成。
