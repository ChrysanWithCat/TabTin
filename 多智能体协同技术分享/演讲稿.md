# 演讲稿：从一个人爽，到一群人接住

> 对应 14 页 PPT，预计 20–25 分钟。括号里是翻页提示和停顿点。

---

## 第 1 页 · 封面

大家好，今天分享一个我最近偶然翻到的开源项目，叫 TabTin。

但我不打算只讲这个项目本身。我想从一个大家都有体感的问题聊起：为什么 AI 让我们个人干活快了，团队却没跟着快起来？

TabTin 是这条线上的一个观察样本。我们会看到，它和最近很热的多智能体协同，其实在填同一道沟。

（翻页）

---

## 第 2 页 · 你让 AI 做的东西，同事接得住吗？

先问大家一个问题。最近有没有遇到过这种场景——你昨天让 AI 帮你做了一下午竞品调研，今天同事接手，第一句话是："这个结论怎么来的？那个数据源链接呢？"

你得翻两百条聊天记录，才能把当时的判断依据找出来。

这不是你不负责。是现在的工具帮你把活干完了，却没帮你把过程留下来。你做完了，上下文在你的对话框里，方法在你的 Prompt 里，判断依据在你的历史记录里。这些东西不会自动变成团队的资产。

（停顿两秒）

这不是某个人不上心，是我们现在用的这些 AI 工具，它设计的时候就是围着"你这一个人"转的。

（翻页）

---

## 第 3 页 · 数字鸿沟

这个鸿沟不是我瞎编的，有统计数字。

左边，个人层面，受控实验里编码任务的完成时间提升在 20% 到 55%。体感上确实快了。当然也有严谨实验发现，资深开发者在熟悉代码上反而慢了 19%——说明这个数字高度依赖任务类型。但方向是对的：个人确实快了。

右边，把视角拉到宏观。经济学家 Acemoglu 估算，十年间 AI 对全要素生产率的贡献只有大约 0.5%。这是偏保守的估算，乐观模型到年均 0.7 个百分点，但量级就在这儿。

这就是"生产率悖论"在 AI 时代的重演。索洛 1987 年就说过："到处都看得到计算机时代，唯独生产率统计里看不到。"

中间隔着测度、时滞、组织再造。今天我们不展开经济学，只聚焦其中一道：**信息从一个人传到另一个人时，在"汇报/交接"这一步被压成了有损摘要。**

（翻页）

---

## 第 4 页 · 单用户这条链，已经被磨得很完整了

现在的 AI coding 工具——Codex、Claude Code——把"一个人怎么和 AI 干活"这条链打磨得很完整。

从最底下一次无状态的 API 请求，到 Agent 循环、记忆注入、沙箱审批、MCP 协议扩展、状态持久，最上面多任务编排，这七层全是围绕你这一个人的 session 跑的。

但你往右边看——多人协作、任务接续、上下文共享、方法复用、执行追溯——这一层，现在的工具基本是空白。

这就是 TabTin 切入的位置。也是接下来多智能体协同这个话题要回应的问题。

（翻页）

---

## 第 5 页 · 一个很自然的想法

面对右边那片空白，技术界很自然地想到一个方向：既然一个人调度 agent 能提效，那多来几个 agent 一起干是不是更快？

这就是最近很热的多智能体协同、Agent Teams 这类概念。

但我读下来发现，这件事比"多个 agent 互相发消息"复杂得多。我们接下来花几分钟把它讲透，因为这是理解后面 TabTin 为什么选那条路的钥匙。

（翻页）

---

## 第 6 页 · 两种拓扑

先别混。这是两种拓扑，不是版本升级。

左边是子代理，星型，主管派活下属汇报，下属之间不能说话。最典型的——安全审查 agent 发现问题，想中途喊正在做性能优化的 agent"别把这个写法用到别处"，子代理架构做不到，因为它们之间零通信。

右边是多智能体协同，网状，队友之间可以直接对话。发现问题的和需要这个信息的直接沟通，信息只传一次。

现状：Codex 目前只做到左边。Claude Code 的 Agent Teams 想做右边，但还在研究预览阶段，工具链还在早期。

（翻页）

---

## 第 7 页 · 有损漏斗

这一页是整个多智能体话题的核心。

左边：子代理架构下，A 子代理花十分钟读了二十个文件，回传给主线程的只有一句"建议方案 B"。但 B 子代理可能恰恰需要知道"A 当时为什么否掉了方案 A 里那个边界条件"——这个细节在 A 压缩成摘要时就被扔了。主线程再转述一次，又衰减一次。

右边：多智能体协同让发现问题的 agent 和需要这个信息的 agent 直接对话，信息只损耗一次。这其实就是我们第 2 页说的"同事接不住你"的 agent 版本。

认知层面也是同一个道理：你自己检查自己的考卷，你会犯的错第二遍还会犯。多个独立视角互相挑错，收敛到同一答案才值得信。

（翻页）

---

## 第 8 页 · 两盆冷水

讲到这里必须泼两盆冷水，不然就变成无脑吹多智能体了。

**第一盆**：多 agent 辩论大约消耗 2 到 5 倍 token。原论文没做"给单 agent 同样多 token"的对照。后来有人补上了，结果发现单 agent 拿同样多的 token 自己深想，不一定差。所以多 agent 买的不是算力效率，是真正的独立视角。

**第二盆**更扎心。2026 年一项针对 7 到 8B 参数模型的研究发现，同质小组辩论不仅没有提升准确性，反而比独立自校正多花了 2.1 到 3.4 倍 token——因为大家一起掉到同一个沟里，还因为"别人也这么说"更自信了。共享同一套训练分布，就共享同一类盲点。

所以那句话记住：**同一个模型开三个实例互相点头，那不叫多智能体，叫一场自我肯定的表演。**

（停顿两秒）

（翻页）

---

## 第 9 页 · TabTin：它选了一条不同的路

讲完多智能体协同的坑，现在来看 TabTin。它是个开源的人机协作平台，AGPL 协议。

它最有意思的不是做了什么，而是没做什么——它没有急着让 agent 之间互相聊天，而是先解决"人接续人的工作"。

四个机制：

第一，**交接 = 冻结上下文，不是甩摘要**。任务交接时冻住对话上下文，带上引用过的文档表格——同事打开就知道你当时怎么判断的。

第二，**人和 Agent 操作同一份结果**。文档、多维表格、PPT、消息都是在线协作对象，Agent 直接编辑，人不用在聊天框和办公软件之间搬运。

第三，**方法固化为可复用的 Agent 角色**。验证过的调研方法、Review 规则、测试步骤，沉淀成角色和 Skill，不靠某个人临时写的 Prompt。

第四，**执行可检查，责任可追溯**。权限、模型、用量、执行记录都在；Agent 干活，但判断和验收仍然是人做。

你会发现，它选的这条路，正好是上一页那条冷水的回响——没有真正异质性的协同，不如不做。它先把人之间的接续做扎实。

（翻页）

---

## 第 10 页 · 三个架构决策

这个项目不是套壳。它开放的是真实产品代码：Electron 桌面端、移动端、服务端、Agent Runtime、实时协作、管理后台。

我读源码时注意到三个架构决策，比功能列表更能说明它想做什么。

**第一，Agent ≠ Device**。Agent 表示"谁参与"，Device 表示"在哪执行"。同一个 Agent 可以在不同电脑上跑——你手机上发起的任务，在桌面 Daemon 上执行。

**第二，交接 ≠ 共享目录**。你的 Workspace 是私有的，任务交接时只带引用材料和上下文，不会把你的整个本地目录甩给同事。

**第三，Shadow Git**。它的检查点叫 Shadow Git——在用户项目目录外面维护一个隐藏仓库，通过 core.worktree 指向你的项目。不污染你自己的 .git。这是"工作可交接"在工程上的具体落地。

当然它现在还是 Public Preview，成熟度参差不齐，这点要有预期。

（翻页）

---

## 第 11 页 · TabTin 站在哪：和 Codex / Claude Code 比

这一页直接对比。

先看设计假设。Codex 和 Claude Code 从头到尾就是给单人用的——Codex 是"派发后走开"，所以用内核级沙箱做硬隔离；Claude Code 是"人在终端前盯着"，所以用 hooks 和 /rewind 做软边界。TabTin 不一样，它假设一个团队，人和 Agent 一起干活。

看最后两行就明白差异在哪：多人协作和工作交接。Codex 没有多人协作；Claude Code 有 Agent Teams，但还在研究预览；TabTin 是 CRDT 原生，人和 Agent 同时编辑同一份文档。工作交接上，那两个工具的会话历史都在你本地，换人就断了；TabTin 是冻结上下文带引用材料，换人接得住。

但它不是全赢。coding 深度不如那两个，沙箱也不是内核级——Codex 有 Seatbelt/Landlock，TabTin 是应用层 judge()。它的定位是：Codex 和 Claude Code 把"一个人跟 AI 干活"磨到了极致，TabTin 站在右边那层空白上，解决"一个人干完了怎么让下一个人接得住"。不是替代品，是补位。

（翻页）

---

## 第 12 页 · 两条路，填的是同一道沟

把今天讲的两条路放在一起看。

左边多智能体协同，保护的是 agent 之间的独立视角，不让它在层级汇报中被压平。右边 TabTin，保护的是人之间的工作上下文，不让它在交接中被丢掉。

方向不同，但你看下面这行——它们填的是同一道沟：**信息从一个工作主体传到另一个工作主体时，别在"汇报/交接"这一步被压成有损摘要。**

这就是为什么我说 TabTin 是个影子——它背后是整个 AI 协作领域正在面对的同一个问题。

（翻页）

---

## 第 13 页 · 不用等平台，今天就能开始

最后不讲大道理，给一个明天就能试的动作。

下次你用 AI 做完一个东西，别只把最终文件丢给同事。多做一步：把"我当时为什么这么判断、参考了哪几个资料、否掉了哪个方案"一起交出去。哪怕就是在文档开头写三行字。

这就是 TabTin 在工程上自动化的事——冻结上下文、带上引用材料。但不用等平台，今天手动就能开始。

多智能体也好，协作平台也好，核心就一句话：**让工作能被下一个人接得住。**

（翻页）

---

## 第 14 页 · 收尾

最后收一句。

AI 真正的效率红利，可能不在一个人用多快，而在一群人能不能互相接住。

TabTin 是 AGPL 的开源项目，现在 Public Preview，感兴趣的可以去 GitHub 跑一跑。我自己也是刚接触，有什么想法欢迎一起讨论。问答环节大家随便问。

谢谢大家。
